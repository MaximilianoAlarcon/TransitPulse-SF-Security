-----------------------MODELOS-----------------------

1) Predicción de volumen de incidentes (Time Series Forecasting)
Input
-----
{
  "timestamp": "2026-02-21 08:00:00",
  "district": "Mission",
  "category": "Larceny Theft",
  "count": 12
}
Output
------
{
  "expected_incidents_next_hour": 15,
  "confidence_interval": [10, 20]
}

2) Clasificación de nivel de riesgo
Input
-----
{
  "hour": 20,
  "day_of_week": "Saturday",
  "district": "Mission",
  "recent_incidents_1h": 18,
  "recent_incidents_24h": 120,
  "category_frequency_24h": 45,
  "open_cases_ratio": 0.65,
  "online_report_ratio": 0.4
}
Output
------
{
  "risk_level": "High",
  "risk_score": 0.82
}

3) Clustering de zonas (detección de “hotspots”)
Input
-----
{
  "lat": 37.7749,
  "lon": -122.4194,
  "timestamp": "2026-02-21T08:00:00",
  "category": "Larceny Theft"
}
------
{
  "cluster_id": 3,
  "cluster_density": 0.87,
  "is_hotspot": true
}

4) Modelo de riesgo sobre rutas (feature engineering + ML)
Input
-----
{
  "incidents_near_route": 25,
  "incidents_last_24h": 10,
  "incidents_last_7d": 80,
  "theft_ratio": 0.6,
  "night_ratio": 0.7,
  "avg_distance_to_route": 120,
  "max_density_segment": 8,
  "hour": 21,
  "day_of_week": "Saturday"
}
Output
------
{
  "risk_score": 0.72,
  "risk_level": "Medium"
}

5) Detección de anomalías
Input
-----
[
  {"t": "08:00", "count": 12},
  {"t": "09:00", "count": 10},
  {"t": "10:00", "count": 35}
]
Output
------
{
  "anomaly": true,
  "severity": "high",
  "expected_range": [8, 15],
  "actual": 35
}














-----------------------TABLAS-----------------------
Para cubrir todos esos modelos, conviene separar las tablas en 3 capas:

raw ingestion
features agregadas
predicciones / resultados de modelos

Y sí, varias necesitan actualización constante, pero no todas con la misma frecuencia.

Te lo dejo ordenado por tabla y por modelo.

1. Tabla base obligatoria
incidents_raw

Guarda cada incidente tal como viene de la API, más algunos campos normalizados.

Columnas
incidents_raw (
    row_id text primary key,
    incident_datetime timestamp,
    incident_date date,
    incident_time time,
    incident_year int,
    incident_day_of_week text,
    report_datetime timestamp,
    incident_id text,
    incident_number text,
    report_type_code text,
    report_type_description text,
    filed_online boolean,
    incident_code text,
    incident_category text,
    incident_subcategory text,
    incident_description text,
    resolution text,
    police_district text,
    data_as_of timestamp,
    data_loaded_at timestamp,

    -- derivados útiles
    incident_hour int,
    report_delay_minutes int,

    -- geografía si existe en otra versión del dataset
    latitude double precision,
    longitude double precision,
    geom geometry(Point, 4326)
)
Para qué sirve

Base para todos los modelos.

Actualización

Sí, constante.
Idealmente:

cada hora
o una vez por día para MVP
2. Tablas de agregación temporal

Estas son las más importantes para forecasting, riesgo y anomalías.

incident_counts_hourly

Agregado por hora.

Columnas
incident_counts_hourly (
    bucket_start timestamp,
    police_district text,
    incident_category text,
    incident_subcategory text,
    total_incidents int,
    open_active_count int,
    filed_online_count int
)
Derivadas
open_active_ratio = open_active_count / total_incidents
filed_online_ratio = filed_online_count / total_incidents
Para qué modelos
predicción de volumen
clasificación de nivel de riesgo
detección de anomalías
Actualización

Sí, constante.
Cada vez que cargas nuevos incidentes, recalculás:

última hora
últimas 24/48 horas por seguridad

5. Tablas para rutas

Columnas

    dest_lon double precision,

11. Respuesta corta a tu duda principal

Sí, necesitan actualización constante, pero no en tiempo real absoluto.

Un esquema razonable sería:

ingesta API: cada 1 hora o cada 1 día
agregados horarios: cada 1 hora
hotspots/grid: cada 6 o 24 horas
predicciones: cada 1 hora o cuando las necesites
riesgo de rutas: on demand
